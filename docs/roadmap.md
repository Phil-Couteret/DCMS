## Phase 4.6 — Multi-tenant user memberships (2026-07-21, added after Phase 4 shipped)

**Status: code complete. Same "needs `prisma migrate deploy` + `prisma generate` before it works" caveat as above — see migration `20260721141428_user_tenant_memberships`.**

Raised directly by you after Phase 4: some staff legitimately work at more than one diving center. The item 2 deferral above (keeping `users.username`/`email` globally unique) turned out to matter here specifically — with the *old* one-row-per-tenant pattern (duplicate `users` rows, one per center, same as the `admin-<slug>` bootstrap accounts), the same real email address couldn't be used on a second account at all, since `email` is a hard global-unique constraint. That's a real, not hypothetical, blocker.

Rather than patch the constraint (which only helps `email`, not the deeper "one person, one login" expectation), added a proper many-to-many model:

1. New table `user_tenant_memberships` (`user_id`, `tenant_id`, `role`, `permissions`, `location_access`, `is_active`) — purely additive, `ON DELETE CASCADE` on both FKs (this table is an access grant, not a business record, so cascading is correct here unlike the `NO ACTION` convention used elsewhere). `users.tenant_id`/`role`/`permissions`/`location_access` stay exactly as they are today and remain each user's *primary* tenant — a person with only one tenant (still the common case) needs nothing beyond that, zero behavior change. `username`/`email` stay globally unique, since a `users` row is now unambiguously "one real person," not "one tenant relationship."
2. `users.service.ts login()`: after password verification, gathers the user's available tenants (primary + any active memberships). Superadmins are untouched (still `tenantId: null`, still switch via header/subdomain per Phase 4 item 4). A regular user with exactly one tenant option logs in immediately, same as before Phase 4.6 existed. A user with 2+ options and no subdomain/header narrowing it down gets `{ requiresTenantSelection: true, tenants: [...] }` back instead of a token — no login attempt is fully authenticated until a tenant is chosen. New endpoint `POST /users/login/select-tenant` (`{ username, password, tenantId }` — re-checks the password rather than inventing a separate short-lived token type, simpler to reason about for one extra `bcrypt.compare()`) completes it, issuing a JWT scoped to that membership's own role/permissions (which can differ per tenant - e.g. instructor at Center A, guide at Center B).
3. Membership management: `POST/DELETE/GET /users/:id/tenant-memberships` to grant, revoke, and list a user's tenants.
4. Frontend: `AdminLogin.jsx` shows a "which center?" popup (per your request for something along those lines) when `login()` returns `requiresTenantSelection`, then completes login via the new endpoint once one is picked.
5. New unit tests in `users.service.spec.ts` cover the selection prompt, successful tenant selection with per-membership role/permissions, and rejection of a tenantId the user has no membership for.

**Done (follow-up):** post-login "switch center" affordance. New authenticated `POST /users/switch-tenant` endpoint (`{ tenantId }`, no password - identifies the user from their existing JWT and re-validates the requested tenant via the same `getTenantOptions()` used by login) plus a "Switch Center" item in `Navigation.jsx`'s user menu, shown only when the user has 2+ tenant options. Selecting one re-tokens and reloads the app. Superadmins are unaffected - they keep their separate header/subdomain switch mechanism.

## Phase 6 — Hardening & operational maturity

Found during a full architecture review (2026-08-10), after Phase 5.2 closed out the oversized-file work. These aren't security holes on the scale of Phase 0, but they're the next layer down: dependency freshness, abuse resistance, container hardening, disaster recovery, and the process gaps (no CI, thin test coverage outside the security-critical path) that make regressions more likely to slip through going forward.

1. ✅ **Dependency vulnerabilities (2026-08-10).** `npm audit fix` (non-breaking) run across all four `package.json`s (root, `backend`, `frontend`, `public-website`). Backend: resolved the one critical finding (`body-parser`) plus most highs; one moderate remains (`@nestjs/core` injection advisory) that needs a NestJS 10→11 major-version bump — deliberately deferred rather than force-applied, since that's a breaking change needing its own test pass, not something to bundle into a routine audit fix. Frontend: 58→30 findings; the remainder is almost entirely inside `react-scripts`' own pinned build-tool chain (webpack-dev-server, postcss, etc.) — `react-scripts` lives in CRA's `dependencies` (not `devDependencies`, which is CRA's own convention) so `npm audit --omit=dev` doesn't actually exclude it, but that code is a build tool that never ships in the static `build/` output actually served to users; the one real production-shipped issue (`react-router`, moderate open-redirect) also needs a major v6→v7 bump, deferred the same way. `public-website`: same pattern, 32 remaining findings, same reasoning. **Both deferred major-version bumps, and the broader false-positive noise from CRA's dependency classification, are best resolved together by the CRA→Vite migration already on this list (item 4 above) rather than patched piecemeal.** Verified after fixing: backend `tsc --noEmit` clean, 35/35 backend tests pass, 40/40 frontend tests pass, and all three apps (`nest build`, both `react-scripts build`) build successfully.
   - **Also fixed as part of this: `package-lock.json` was gitignored repo-wide (all four of them — root, backend, frontend, public-website — were untracked).** This meant `npm audit fix` only ever fixed a given machine's local `node_modules`, not the repo — the next `npm install` anywhere else (Docker build, ZBOX deploy, another developer's clone) could silently re-resolve to different, potentially still-vulnerable transitive versions, and there was no way to get a reproducible install. Removed the `package-lock.json` line from `.gitignore` and committed all four lockfiles. This is arguably the more important fix of the two — without it, today's audit-fix work wouldn't have outlived the sandbox session.
2. ✅ **Rate limiting + security headers (2026-08-10).** Added `@nestjs/throttler` (v6.5.0, compatible with the current Nest 10.x — no framework bump needed) and `helmet` (v8.3.0). App-wide default: 100 requests/60s per IP via a global `ThrottlerGuard` registered as a second `APP_GUARD` alongside the existing `JwtAuthGuard`. The three credential-checking endpoints (`POST /users/login`, `POST /users/login/select-tenant`, `POST /partner-auth/login`) get a tighter `@Throttle` override — 10/60s — since those are what brute-force/credential-stuffing actually targets, not the general API. `helmet()` applied in `main.ts` with `contentSecurityPolicy: false` (the Swagger UI served from the same app needs inline scripts/styles; revisit if Swagger ever moves to its own origin). Caught and fixed a real regression risk before it shipped: `unauthenticated-routes.e2e-spec.ts` fires 100+ sequential requests (one per registered route) from a single test client to verify the auth guard — with the new global throttle active it would have started returning 429 partway through and been indistinguishable from a route that failed to reject an unauthenticated request. Fixed by overriding `ThrottlerGuard` to a no-op for that specific suite (`.overrideGuard(ThrottlerGuard).useValue({ canActivate: () => true })`) since it's testing auth, not rate limiting. Added a new `login-rate-limit.e2e-spec.ts` that fires 12 login attempts against a stubbed Prisma and asserts the first 10 get 401 (bad credentials) and at least one of the last 2 gets 429. Verified: `tsc --noEmit` clean, 35/35 unit tests pass, both relevant e2e suites pass (`login-rate-limit`, `unauthenticated-routes`), `nest build` succeeds.
3. ✅ **Docker non-root (2026-08-10).** Backend: switched the final stage to run as the `node` user the official `node:20-bullseye-slim` image already provides (uid 1000), rather than root — added `RUN chown -R node:node /app` (needed since files land as root during `COPY`) before `USER node`. Nothing in `docker-entrypoint.sh` or the app needs root: no privileged port (3003), no writes outside `/app`, and the one external mount (`/init/seeds`, docker-compose only) is read-only. Frontend and public-website were the harder case — both serve via `nginx:alpine` on port 80, and nginx's stock image needs root just to bind that privileged port, so a bare `USER` directive would have broken the container rather than hardened it. Switched both to `nginxinc/nginx-unprivileged:alpine`, the official variant built to run entirely as a non-root user (uid 101) on an unprivileged port (8080) with no further config needed. Updated the one call site each: `docker-compose.yml` (`3000:8080`), and `deploy/zbox/k8s/admin.yaml` / `public.yaml` (`containerPort`/`targetPort` → `8080`; the Kubernetes `Service`'s external `port: 80` and the ingress's `service.port.number: 80` are unaffected — only the container-internal port moved). Not verified via `docker build` (no Docker available in this sandbox) — verify on a machine with Docker before deploying, same caveat as the backend change.
4. ✅ **Automated production database backups (2026-08-10).** Added a `postgres-backup` Kubernetes `CronJob` (`deploy/zbox/k8s/postgres-backup-cronjob.yaml`) running `pg_dump --format=custom` daily at 03:15, writing to a separate PVC (`postgres-backup-pv.yaml`, `/data/dcms/postgres-backups` — deliberately a different host directory than the live DB's `/data/dcms/postgres`, so a bad query or accidental deletion in the live data doesn't also destroy the backups sitting next to it) and pruning dumps older than 14 days. Same `postgres:15-alpine` image as the live DB so `pg_dump`'s version always matches what it's dumping. Added `deploy/zbox/scripts/restore-backup.sh` (`list` / `restore <file>`) — spins up a one-shot pod mounting the backup PVC read-only, runs `pg_restore --clean --if-exists --no-owner`, requires typing the filename back to confirm before touching the live DB. Wired both new manifests into `deploy.sh` (host directory creation/chown, `kubectl apply`) and documented the whole flow in `deploy/zbox/README.md`. **Known remaining gap, called out explicitly rather than silently left out:** backups live on the same physical disk as the live database (different directory, same disk) — this protects against accidental deletion/corruption but not hardware failure. Off-box replication (rsync/rclone to another machine or object storage) wasn't added since it depends on what remote target is actually available, which wasn't known at the time; flagged in the README as the next step.
