## Phase 4.6 — Multi-tenant user memberships (2026-07-21, added after Phase 4 shipped)

**Status: code complete. Same "needs `prisma migrate deploy` + `prisma generate` before it works" caveat as above — see migration `20260721141428_user_tenant_memberships`.**

Raised directly by you after Phase 4: some staff legitimately work at more than one diving center. The item 2 deferral above (keeping `users.username`/`email` globally unique) turned out to matter here specifically — with the *old* one-row-per-tenant pattern (duplicate `users` rows, one per center, same as the `admin-<slug>` bootstrap accounts), the same real email address couldn't be used on a second account at all, since `email` is a hard global-unique constraint. That's a real, not hypothetical, blocker.

Rather than patch the constraint (which only helps `email`, not the deeper "one person, one login" expectation), added a proper many-to-many model:

1. New table `user_tenant_memberships` (`user_id`, `tenant_id`, `role`, `permissions`, `location_access`, `is_active`) — purely additive, `ON DELETE CASCADE` on both FKs (this table is an access grant, not a business record, so cascading is correct here unlike the `NO ACTION` convention used elsewhere). `users.tenant_id`/`role`/`permissions`/`location_access` stay exactly as they are today and remain each user's *primary* tenant — a person with only one tenant (still the common case) needs nothing beyond that, zero behavior change. `username`/`email` stay globally unique, since a `users` row is now unambiguously "one real person," not "one tenant relationship."
2. `users.service.ts login()`: after password verification, gathers the user's available tenants (primary + any active memberships). Superadmins are untouched (still `tenantId: null`, still switch via header/subdomain per Phase 4 item 4). A regular user with exactly one tenant option logs in immediately, same as before Phase 4.6 existed. A user with 2+ options and no subdomain/header narrowing it down gets `{ requiresTenantSelection: true, tenants: [...] }` back instead of a token — no login attempt is fully authenticated until a tenant is chosen. New endpoint `POST /users/login/select-tenant` (`{ username, password, tenantId }` — re-checks the password rather than inventing a separate short-lived token type, simpler to reason about for one extra `bcrypt.compare()`) completes it, issuing a JWT scoped to that membership's own role/permissions (which can differ per tenant - e.g. instructor at Center A, guide at Center B).
3. Membership management: `POST/DELETE/GET /users/:id/tenant-memberships` to grant, revoke, and list a user's tenants.
4. Frontend: `AdminLogin.jsx` shows a "which center?" popup (per your request for something along those lines) when `login()` returns `requiresTenantSelection`, then completes login via the new endpoint once one is picked.
5. New unit tests in `users.service.spec.ts` cover the selection prompt, successful tenant selection with per-membership role/permissions, and rejection of a tenantId the user has no membership for.

**Done (follow-up):** post-login "switch center" affordance. New authenticated `POST /users/switch-tenant` endpoint (`{ tenantId }`, no password - identifies the user from their existing JWT and re-validates the requested tenant via the same `getTenantOptions()` used by login) plus a "Switch Center" item in `Navigation.jsx`'s user menu, shown only when the user has 2+ tenant options. Selecting one re-tokens and reloads the app. Superadmins are unaffected - they keep their separate header/subdomain switch mechanism.
